# ぼうけんカード メーカー — 仕様書 / 引き継ぎドキュメント

最終更新: Claude.ai チャットでの開発セッションからの書き出し（2026-09-19）

## 1. 何を作っているか

未就学児（作者の息子）と親が一緒に遊ぶための、QRコードを使った宝探し（脱出ゲーム風スカベンジャーハント）アプリ。

- 物理カード（連番のQRコードが印刷された紙）を家の中に隠す
- タブレット/スマホでアプリを開き、カメラでQRを読み取ると、次にどこを探せばいいかのヒントが絵文字＋日本語音声（Web Speech API）で出る
- 「協力プレイ」モード：1つのヒントに対して複数枚のカードが割り当てられ、全部見つからないと次に進めない（兄弟・友達同士で「誰が見つけた／誰が持つ」の揉め事を避ける設計）
- 親が「編集」画面でヒントの中身・カード枚数・アイコンなどを自由に作れる「コンテンツエディター」が本体機能
- 複数の「プリセット」（テーマ違いの冒険セット）を保存・切り替え・複製でき、JSONテキストとしてエクスポート/インポートして他の家庭と共有できる
- カードは0〜100番まで汎用的にQR生成しておき、「何枚印刷するか」を指定してPDFに書き出す（コンビニのネットプリント等にそのまま出せる）

対象ユーザーは未就学児なので、文字は極力ひらがな中心・大きく・シンプルにしている。

## 2. 現在の実装形態

**単一の自己完結HTMLファイル**（`index.html`）。ビルドステップなし、フレームワークなし、バニラJS。

理由：Claude.ai のアーティファクト機能（ブラウザ内で完結するプレビュー環境）で開発していたため。今回コード管理に移行するにあたり、この制約は外れるので、必要なら以下のようなリファクタも検討可：
- Vite等でのモジュール分割
- 依存ライブラリのローカルバンドル（現在はCDN読み込み。下記「外部依存」参照）
- PWA化（オフライン対応・ホーム画面追加）

ただし「単一HTMLファイルをそのままレンタルサーバーや GitHub Pages に置くだけで動く」という現状のシンプルさにも価値があるため、リライトするかどうかは運用方針次第。

## 4. データモデル（localStorage）

すべてブラウザの `localStorage` に保存。サーバー・DB一切なし。

### 4.1 プリセットストア

キー: `advcards_store_v1`

```json
{
  "activeId": "sample-dino",
  "presets": {
    "sample-dino": {
      "id": "sample-dino",
      "name": "きょうりゅうたんけん（サンプル）",
      "icon": "🦕",
      "stageCount": 5,
      "groupSize": 1,
      "hints": [
        { "emoji": "🥚", "text": "たまごの あるところを さがしてね" },
        { "emoji": "🦴", "text": "..." },
        ...
        { "emoji": "🏆", "text": "やったー！さいごまで たどりついたね！..." }
      ]
    }
  }
}
```

- `hints` 配列の長さは常に `stageCount + 1`
  - `hints[0]` = スタート直後に出るヒント（次に探すのはカード#1〜#groupSize）
  - `hints[1..stageCount-1]` = 各ステージクリア時のヒント
  - `hints[stageCount]` = ゴールメッセージ
- `groupSize` = 1ステージあたり同時に集める必要のあるカード枚数（協力プレイ用。1ならソロ）

### 4.2 進行状況（プリセットごと）

キー: `advcards_progress_<presetId>`（例: `advcards_progress_sample-dino`）

```json
{ "currentStage": 2, "found": [true, false] }
```

- `currentStage` = 今スキャン待ちのステージ番号（0はスタート待ち状態）
- `found` = 現在のステージ内で、`groupSize` 枚のうちどれが見つかったか（`groupSize<=1`のときは常に空配列）
- プリセットを切り替えると、そのプリセット専用の進行状況が読み込まれる（プリセット間で進捗は独立）

## 5. QRコードのエンコード方式

QRの中身は最小限の文字列のみ：

```
DINOQUEST:<番号>
```

- `番号 = 0` → 「スタート」カード（全プリセット・全印刷ロットで共通の1枚。人数に関係なく常に1枚だけ）
- `番号 = 1, 2, 3, ...` → 連番の物理カード。ヒントの中身は一切QRに埋め込まれておらず、アプリ側のプリセットデータを見て「この番号は今のプリセットの何ステージ目に属するか」を計算する

**⚠️ 引き継ぎ時に検討してほしい点**：`DINOQUEST:` というプレフィックスは、プロジェクト初期に「恐竜限定」だった頃の名残であり、今の汎用「ぼうけんカード」というコンセプトとは合っていない。

- すでに試作印刷した0〜10番のカード（PDF）はこの文字列でQRを焼いてしまっている
- 今後プレフィックスを変える場合、それ以前に印刷したカードは（アプリ側の判定文字列を変えない限り）そのまま使えるので実害はないが、コードの読みやすさ・今後の混乱防止のため、本格リリース前に `ADVCARD:` 等の中立的な文字列に変えておくことを推奨（1箇所の文字列定数を変えるだけで済むよう、現状すでに `'DINOQUEST:'` は複数箇所にリテラルで散らばっているので、コード移行時に定数化するとよい）

## 6. カード番号 → ステージ の計算ロジック

```js
function totalCards(preset) {
  return preset.stageCount * preset.groupSize;
}

function rangeOfStage(preset, stageNumber) {
  const g = preset.groupSize;
  return { from: (stageNumber - 1) * g + 1, to: stageNumber * g };
}

function stageOfCard(preset, cardNumber) {
  return Math.ceil(cardNumber / preset.groupSize);
}
```

例：`groupSize = 3` のとき、ステージ1は物理カード#1〜#3、ステージ2は#4〜#6…という具合に、印刷するカード自体はただの連番のままグルーピングだけソフトウェア側で行う。これにより「協力プレイ用に人物ごとのQRを刷り分ける」必要がなくなり、印刷物を汎用化できている（これは開発初期に「QRを毎回作り直すのが面倒」という指摘を受けて設計を変えた結果の形）。

## 8. PDF書き出しの仕組み（重要な技術判断の経緯）

現在の実装：**ブラウザ内で完結するクライアントサイド生成**。

1. 各カードをその場でHTML要素として組み立てる（`buildCardEl()`）— 見た目はアプリ内の配色・フォントをそのまま流用
2. `html2canvas` でそのDOM要素を画像化（`scale:3` で高解像度化）
3. `jsPDF` でA4ページに2列×3行のグリッド配置、必要なページ数分ループ
4. 完成したら `doc.save('bouken-cards.pdf')` でダウンロード

### なぜこの方式になったか（過去に試して失敗した方法）

最初は **Python + reportlab** でサーバーサイド（Claudeの実行環境内）にPDFを生成しようとしたが、以下の問題に当たった：

- reportlab組み込みのCID日本語フォント（`HeiseiKakuGo-W5` 等）は、実際のグリフ（字形）データを埋め込まず「ビューア側が日本語フォントを持っている前提」で動作する。poppler（`pdftoppm`等）ベースのビューアではグリフが一切表示されず、文字が完全に消える不具合が発生した
- システムに入っていた `Noto Sans CJK` はCFF（PostScriptアウトライン）形式のOpenTypeで、reportlabの `TTFont` はTrueType（glyfテーブル）しか扱えず登録エラーになった
- 最終的に `/usr/share/fonts/truetype/fonts-japanese-gothic.ttf`（IPAゴシック、TrueType形式）を見つけて解決したが、この経験から「日本語フォントのPDF埋め込みは環境依存の罠が多い」という教訓を得た

→ その後「印刷用カードのデザインをアプリ側で毎回作り直せるようにしたい」「Pythonバックエンドなしでブラウザだけで完結させたい」という要望もあり、**html2canvas + jsPDF方式に全面移行**。ブラウザの実際のフォントレンダリングをそのまま画像化するため、フォント埋め込み問題が原理的に発生しない。

この経緯から、もしコード移行後にPDF生成を作り直す/最適化する場合、reportlab等のサーバーサイドPDF生成に戻すなら日本語フォント埋め込みの罠に再度注意すること。

## 9. デザイントークン

Anthropicの `frontend-design` スキル（AI生成デザインにありがちな“テンプレっぽさ”を避けるためのガイド）に沿って設計。

  - `--amber` (#E8A33D)：番号バッジ等のアクセント
  - `--leaf` / `--leaf-dark` (#3F7350 / #244A34)：ジャングル/冒険感のベースグリーン

- **モチーフ**：👣（あしあと）を連番・進行の視覚的な目印として使用

## 10. 既知の制約・今後の検討課題（TODO）

1. **QRプレフィックス `DINOQUEST:` の恐竜由来ネーミング**（§5参照）→ リリース前に中立的な名前に変更推奨
2. **完全オフライン非対応**：CDN依存のため初回ロード時はネット接続が必要。台風・キャンプ等のオフラインシナリオを重視するなら、依存ライブラリのローカルバンドル＋Service Worker化を推奨
3. **PDF書き出しの速度**：カード1枚ごとに `html2canvas` を直列実行しているため、100枚出力すると数十秒〜数分かかる可能性がある。並列化やCanvas再利用による高速化の余地あり
4. **共有機能はコピペJSONのみ**：QRやリンクでの共有、クラウド経由の共有はサーバーが必要になるため未実装
5. **カメラスキャンはHTTPS/localhost必須**（`getUserMedia`のブラウザ制約）。どこにホスティングするにせよこの点は変わらない
6. **自動テストなし**：現状すべて手動確認（Playwright等でのビジュアル確認はチャット内デバッグ時に部分的に実施したのみ）
7. **多言語対応なし**：現状すべて日本語ハードコード。海外展開や英語話者向けを考えるなら文言の外部化が必要

## 11. 開発の経緯（意思決定ログ・要約）

未来の自分（または引き継ぐ開発者）が「なぜこうなっているか」を無駄に再考しなくて済むように、主要な設計変更の流れを記録しておく。

1. 恐竜テーマ・1人プレイ前提の「宝探しアプリ」としてスタート（`dino-quest.html`）
2. 「兄弟・友達で協力プレイしたい、カードの奪い合いを避けたい」という要望 → 最初は「1ステージ=プレイヤー人数分のQR（各人専用）」を実装
3. 「同じQRを毎回刷り直すのは面倒、使い回したい」という指摘 → QRは単純な連番のみにし、「何番から何番までを集めればクリアか」というグルーピングをアプリ側の設定（`groupSize`）だけで決める方式に変更（現行方式）
4. 「恐竜限定をやめて汎用化したい」「コンテンツエディターを主機能にしたい」「プリセットを共有したい」「カードは0〜100まで先に用意して印刷枚数だけ選べるようにしたい」という要望 → プリセット管理機能・JSON共有・PDF一括書き出し機能を追加（`adventure-cards.html`）
5. 「編集がタブだと分かりにくい」→ 編集をプリセットカードからの導線に変更
6. 「カードの数字・文字が小さい、スタート等の表記をひらがなに」→ カードデザインの文字サイズ拡大、カタカナ表記をひらがな寄りに変更、スタートバッジを🚩アイコン化
7. 今回：Claude.aiのアーティファクト運用（リリース・バージョン管理のしにくさ）を理由に、Claude Codeでの開発に移行

## 13. 移行後の変更点（Claude Code / Vite化）

- 単一HTML → Vite + バニラJS（ES modules）。依存はnpm管理・ローカルバンドル、フォントは `@fontsource/zen-maru-gothic`。
- QRプレフィックスを `DINOQUEST:` → `ADVCARD:` に変更（§5）。`src/lib/qr.js` の定数 `QR_PREFIX` に集約。
  試作印刷済みの `DINOQUEST:` カードも読み取り可（`LEGACY_PREFIXES`）。**新規に印刷するカードは `ADVCARD:`**。
- PWA化（vite-plugin-pwa、全アセットprecache）でオフライン対応（§3, §10-2 対応済み）。
- QR生成は `qrcodejs` → `qrcode`（npm）に変更。QRコードのプレビュー/PDFはPromise化。
- ユニットテスト追加（QR符号化・ステージ計算）。

### 13.1 カードサイズ（はがきサイズのラミネート対応）

- カードは縦長 **94×140mm**（`src/lib/pdf.js` の `CARD_MM` と `.pdf-card` のCSSで定義）。はがきサイズ(100×148mm)のラミネートポーチに、シール部の余裕（各辺3〜4mm）を残して収まる。
- PDFはA4に **2列×2行（1ページ4枚）**、各カード四隅にトンボ付き。切り抜いてそのままポーチに入れられる。
- 寸法を変えるときは `CARD_MM` と `src/style.css` の `.pdf-card` 内の各mm指定をセットで調整すること。
- PDFの画像はFAST圧縮（未圧縮だと5枚で34MBになるため）。

### 13.2 カード枚数をヒント単位に変更

- `preset.groupSize`（プリセット共通）を廃止し、**各ヒント `hints[i].cardCount`（i>=1、1〜5枚）** に変更。`hints[i]` を出すために集めるカード枚数を表す（`hints[0]`＝スタート直後のヒントは枚数なし）。
- カード番号の割り当ては累積: ステージ1がカード#1〜、次のステージはその続き…（`src/lib/stages.js`）。
- 旧形式（`groupSize`）のデータは、読み込み時・インポート時に `normalizePreset()` で各ヒントの `cardCount` に自動変換される。
- 「いんさつ」タブに、いまのプリセットで使うカード番号の範囲と枚数を表示。

### 13.3 読み上げ音声

- `src/lib/speech.js`: 端末の日本語音声から自動で聞き取りやすいもの（Natural/Online/Enhanced/Google等を優先）を選ぶ。プリセットタブの「よみあげの こえ」で声と速さ（既定0.85）を変更可能（localStorage `advcards_voice_v1`）。
- ひらがなの分かち書きの空白は読点に置換して区切りをはっきり読ませる。
- 音声そのものは端末(OS/ブラウザ)依存。より高品質にするには、iOS/Macは「設定→アクセシビリティ→読み上げコンテンツ→声」で拡張音声をダウンロード、Edgeは Natural 音声が使える。

### 13.4 効果音と進行ロジック

- `src/lib/sfx.js`: Web Audio で合成する効果音（見つけた／全部そろった／ゴール／スタート／既読）と振動。プリセットタブでオン/オフ可。同じカードをかざし続けても2.5秒は連発しない。
- `src/lib/progress.js`: スキャン結果の判定（`applyScan`）と進行状況の整合（`normalizeProgress`）を純粋関数に分離してテスト化。
- 不具合修正: 同じ枚数(2枚以上)のステージが連続すると、前ステージの「全部見つけ済み」が持ち越されて次のスキャンが既読扱いになり進行不能になっていた（元の単一HTML版からの潜在バグ）。ステージ完了時に found を必ず作り直し、保存済みの壊れた進行状況も読み込み時に自己修復する。

### 13.5 スキャン画面のカード番号表示

- 「たんけん」画面の上部に、いま探すカード番号を大きなチップ（例: #2 #3 #4）で表示。複数枚のときは見つけたカードに ✅ が付き「1 / 3 まい」を表示。スタート前は「スタートカードを よみとってね」。
- ヒント表示画面にも「つぎは この カードを さがそう」と次のカード番号を表示。

### 13.6 スキャンの無反応対策

- 読み取ったが「今は使えない」カード（スタート前・別ステージ・範囲外・スタート再読み取り）、およびぼうけんカード以外のQRに対して、トースト＋音で理由を伝える（以前は無言で無視していて「読まない」ように見えた）。
- カメラ起動要求に世代番号を付け、停止/再起動と競合して遅れて届いたストリームを破棄（二重起動・カメラが残る問題の予防）。

### 13.7 タブレット(横向き)レイアウト

- 幅900px以上（横向きタブレット）: ナビを左レールに、各画面を2カラム化（プリセット=一覧|共有・こえ、編集=設定|ヒント一覧、いんさつ=設定|プレビュー、たんけん=カメラ(大)|探すカード番号、ヒント表示=カード|ボタン）。文字・ボタン・番号チップも拡大。
- 700〜899px（縦向きタブレット）: 1カラムのまま幅760pxに拡大。スマホ(縦)は従来どおり下部ナビ。
- PWAの向き固定(portrait)を解除（manifest orientation: any）。**インストール済みのPWAは、一度削除して入れ直すと反映される。**

### 13.8 遊ぶ子ども(5歳児)向けの操作性

- 想定: 操作するのは5歳児（編集は親）。ヒント表示画面のボタンは巨大化（スマホで高さ約100px以上、タブレットで約150px）、文字も大きく、押すと沈む立体ボタン。
- 主ボタン「#nの カードを よみこむ」（オレンジ、最上段）と、「🔊 もういちど きく」「🔄 もういちど あそぶ」。読めない漢字・むずかしい語は避け、ひらがな中心。

### 13.9 メニューの収納（長押しで再表示）

- メニュー末尾の「🔒 かくす」でナビを隠せる。隠すと左下に小さな 🔒 が残り、**タップだけだと「ながおしで ひらく」と案内、約0.8秒の長押し（リングが満ちる）で再表示**。状態はlocalStorage(`advcards_navhidden_v1`)に保存され、再読み込みしても保たれる。
- 目的: 遊ぶ子どもがナビを押して画面が変わってしまうのを防ぐ。

### 13.10 カードの向き（インカメラ既定）

- カメラの既定を**インカメラ(user)**に変更（iPad等で使う想定）。スキャン画面右上の 🔄 で切替（選択は localStorage `advcards_cam_v1` に保存）。インカメラ時は映像を左右反転表示（読み取りは反転前の映像で行うため影響なし）。

### 13.11 お祝いの演出

- `src/lib/fx.js`: 画面全体にかぶせる透明canvasで紙吹雪・絵文字(⭐🎉✨)を描く（依存なし、`prefers-reduced-motion` では量を減らす）。
  - カードを1枚見つけた: 上のほうで小さくキラッ
  - ヒントが出る/スタート: 画面下から紙吹雪
  - ゴール: 左右から約3.5秒間に何度も打ち上げ＋星の雨、「🎉 おめでとう！ 🎉」バナー、トロフィーが弾む

### 13.12 ミッションモード

- 背景: 息子は「探す」より「ミッションを達成→カードをもらう→読み込ませる」流れが楽しい（実プレイの所見）。
- プリセットに `mode: "mission" | "search"` を追加（未指定は従来どおり `search`=たからさがし。新規プリセットは `mission`）。編集画面の「あそびかた」で切替。
- `src/lib/words.js` にモード別の文言を集約（ヒント→ミッション、「さがそう」→「クリアしたら この カードを もらおう」、「みつけた」→「ゲット！」など）。データ構造(hints/cardCount)は共通。
- `src/lib/missions.js`: ミッションの例25個（ジャンプ10かい、へんな顔、おてつだい等）。各行の「💡 ミッションの れいを いれる」と、一括の「🎲 からっぽの ミッションを れいで うめる」（入力済み・ゴールは上書きしない）。

### 13.13 配布用プリセット

- `docs/presets/enniichi-3nin.json`: おうち縁日用の「3人協力ミッション」5個（カード各3枚＝1人1枚、計15枚＋スタート）。アプリの「プリセット → もらったプリセットを貼り付けて取り込む」に中身を貼り付けて使う。

### 13.14 重ねて浮かび上がるシート（マイラ用）

- `scripts/make-overlay.mjs` が `docs/overlay/` に、3枚重ねるとポップコーンの絵が完成するA4・600dpi・黒1色のレイヤー(PDF/PNG/SVG)を出力（`node scripts/make-overlay.mjs`）。1枚だけだと絵の断片。四隅の十字と外枠で位置合わせ、上部の●の数(1〜3)で3人に1枚ずつ配る。
- 縁日プリセットの4番目のミッション「3まい かさねる」→ポップコーンが浮かび上がる→5番目「ポップコーンを つくろう」につながる。

### 13.15 ミッションの並べ替え・追加・削除

- 編集画面の各行に ▲▼（上下に移動）と 🗑（削除）、行と行の間に「＋ ここに ミッションを ふやす」を追加。ゴールは固定（動かさない・消さない・後ろに足さない）。上限は15個。
- 並べ替えは**文章と絵文字だけ**が入れ替わり、カードの枚数は「行の位置」についたまま。追加した行は上の行と同じ枚数、削除すると後ろの行が繰り上がる。ロジックは `src/lib/hints.js`（テスト付き）。

### 13.16 「たからさがし」モードの廃止

- 「あそびかた」の切り替えをやめ、**ミッション型に一本化**（違いが分かりにくく、学習コストが増えるため）。`preset.mode` は廃止し、読み込み時・インポート時に取り除く。以前 `search` だったプリセットもミッションの文言で表示される（データ構造は共通なので中身は消えない）。
- `src/lib/words.js` は `WORDS`（ミッション文言の定数）のみ。新規インストール時のサンプルは「きょうりゅうミッション」に変更。

### 13.17 ミッション例ボタンの撤去

- 「💡 ミッションの れいを いれる」「🎲 からっぽの ミッションを れいで うめる」と `src/lib/missions.js` を撤去（履歴には残っている）。代わりにテーマ別の配布プリセット（モーニング/ナイトルーティン等）を検討中。

### 13.18 組み込みテーマ別プリセット

- アプリに最初から入るプリセット（`src/lib/builtin-presets.js`）: **あそび**＝きょうりゅうミッション、**せいかつ**＝モーニングルーティン／ナイトルーティン。プリセット一覧はカテゴリー（あそび → せいかつ → じぶんの ぼうけん）ごとにまとめて表示。
- 既存の端末にも次回起動時に追加される（`store.seeded` に追加済みIDを記録し、ユーザーが削除したものは復活させない）。手を入れていない旧サンプル(恐竜)は新内容に置き換え、編集済みのものは内容を保ったまま category だけ付ける。自作・取り込みのプリセットは「じぶんの ぼうけん」。
- ルーティンのミッション内容は初版。実際に使いながら文言を手直しして調整する。

### 13.19 組み込みプリセットの改訂の仕組み（rev）

- `builtin-presets.js` の各プリセットに `rev` を持たせ、内容を直したら rev を上げる。次回起動時、**手を入れていない**端末では新しい内容に置き換わる（判定は保存時の署名 `baseSig` と現在の内容の一致。編集済みは触らない、削除済みは復活しない）。置き換わったプリセットの進行状況は破棄される。
- 過去に配った版（署名なし）は `LEGACY_SIGS` の完全一致で「未編集」と判定する。
- モーニングルーティン rev2: 「カーテン」「洗顔」を削除、「きがえ」を「おきがえを しよう」に、最初のミッションを「といれ」に。

### 13.20 きほんから えらぶ（基本ミッション）

- `src/lib/basic-missions.js` に毎日の基本ミッション16個（といれ／てあらい／うがい／はみがき／おきがえ／パジャマ／あさごはん／ばんごはん／おふろ／かたづけ／おでかけじゅんび／くつ／おみず／かみ／えほん／ねるじゅんび）。
- 編集画面: 各ミッション行の「📋 きほんから えらぶ」でその行に入れ替え、行間の「＋ ここに ミッションを ふやす」で選んだものをその位置に挿入（つづけて何個でも選べる。「✏️ じぶんで かく」は空の行を追加）。

- モーニングルーティン rev3: 最後のミッションを「みじたくを しよう。てぃっしゅと はんかちは もった？」に（「おでかけの じゅんび」は範囲が広すぎるため）。基本ミッションの「おでかけじゅんび」も「みじたく」に同じ文言で変更。

- ナイトルーティン rev2: 「でんきを けして、おふとんに はいろう」を削除し、絵本を「えほんを 1さつ よもう」に。端末は寝室に持ち込まず**リビングで最後のカードを読み込み、最後のメッセージ「おやすみなさい」**で終える前提（寝室への持ち込みを推奨しない）。基本ミッション: 「かみ」→「どらいやーで かみを かわかそう」、「えほん」から「おふとんで」を除き、「ねるじゅんび」を削除。

- ナイトルーティン rev3: 最初のミッションを「おかたづけを しよう」に（対象を「おもちゃ」に限定しない）。基本ミッションの「かたづけ」も同文言に。

- 基本ミッションから「くつ」を削除（靴を履いた子にカードを渡すと、また脱いでスキャンしに行ってしまうため）。
